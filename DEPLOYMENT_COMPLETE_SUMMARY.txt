THE PROBLEM & THE FIX
════════════════════════════════════════════════════════════════════════════════

PROBLEM:
  Race condition between pill fetch and payment in open() endpoint
  - No atomic locking of pill during open-to-submit window
  - Two players could both fetch pill as 'available'
  - Both would proceed to charge before either answered
  - Result: Duplicate plays for same pill

ROOT CAUSE:
  UNIQUE(pill_id, player_id) prevents SAME player twice
  But allows DIFFERENT players simultaneously
  No global consumption guarantee during concurrent opens

THE FIX:
  Add atomic pill claiming state machine:
    available → [ATOMIC CLAIM: available→opening] → [charge] → [answer] → played
  
  How it works:
    1. Player tries to open pill
    2. RPC atomically: UPDATE pills SET status='opening' WHERE id=pill AND status='available'
    3. If UPDATE succeeds: Player owns the pill
    4. If UPDATE fails: Another player already owns it → reject
    5. If billing fails: Revert pill back to 'available'
    6. If answer submitted: Update pill to 'played'

IMPACT:
  ✓ Prevents any second player from opening during first player's attempt
  ✓ Closes the race condition window
  ✓ Maintains per-player tracking (pill_plays unchanged)
  ✓ Automatic rollback if billing fails
  ✓ Backward compatible with existing data
